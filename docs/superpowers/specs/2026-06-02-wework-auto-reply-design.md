# ChaserPA 需求文档（PRD）

> **版本**：v1.0  
> **日期**：2026-06-02  
> **目标**：基于 Android AccessibilityService 实现企业微信指定群的消息监控与自动回复，解决前台运行时通知弹框缺失导致的消息漏采问题。

---

## 1. 项目概述

ChaserPA 是一款 Android 无障碍辅助应用，通过监听企业微信（`com.tencent.wework`）的无障碍事件和 UI 树结构，实现以下核心能力：

1. **指定群消息采集**：只监控用户配置的目标群，忽略其他群和私聊。
2. **消息推送后台**：将采集到的文本消息推送到用户自有的后台服务，由后台决策回复内容。
3. **自动回复执行**：根据后台返回的回复内容，通过 UI 自动化模拟点击、输入、发送操作。
4. **仅处理文本消息**：图片、语音、视频、表情等非文本内容直接忽略。

### 1.1 核心痛点

当前实现依赖系统通知弹框（`TYPE_NOTIFICATION_STATE_CHANGED`）来捕获新消息，但存在以下盲区：

- **企业微信在前台运行时**，部分系统（尤其 OPPO ColorOS）不会弹出新消息通知，导致消息完全丢失。
- 后台运行或息屏状态下，通知监听正常工作；但用户打开企业微信查看消息后，新消息不再触达。

### 1.2 解决方案

引入 **混合监控模式**（通知监听 + UI 轮询兜底）：

- **后台状态**：优先通过通知事件采集，省电且实时。
- **前台状态**：通过定时扫描企业微信 UI 树主动提取消息，填补通知盲区。
- 同时提供 **纯轮询模式** 开关，供通知不稳定的环境使用。

## 2. 术语表

| 术语 | 说明 |
|------|------|
| **AccessibilityService** | Android 无障碍服务，可监听 UI 事件、遍历节点、模拟操作。 |
| **UI 轮询** | 定时遍历企业微信的 AccessibilityNodeInfo 树，从聊天记录中提取消息。 |
| **通知监听** | 通过 `TYPE_NOTIFICATION_STATE_CHANGED` 事件解析通知栏内容获取消息。 |
| **消息列表页** | 企业微信打开后默认显示的会话列表页面（`RecyclerView id=cxl`）。 |
| **聊天详情页** | 点击进入某个群聊后显示的完整聊天记录页面。 |
| **去重 Key** | 用于判断消息是否已采集过的标识，由群名、发送者、内容、时间窗口组成。 |
| **置顶群** | 用户在消息列表中置顶固定的群，始终显示在 RecyclerView 顶部，无需滚动查找。 |

| F-07 | 跨通道消息去重 | P0 | 通知和 UI 轮询两种来源的消息共享去重缓存，避免重复推送。 |

### 3.2 消息推送

| 编号 | 需求 | 优先级 | 说明 |
|------|------|--------|------|

| F-10 | 失败重试与本地队列 | P1 | 网络异常时本地缓存，最多保留 100 条，恢复后批量重试。 |

| F-12 | 串行执行回复任务 | P0 | 多个回复任务进入队列，单线程依次执行，避免 UI 冲突。 |
| F-13 | 自动回复总开关 | P1 | 用户可关闭自动回复，仅采集和推送。 |
| F-14 | 回复完成后返回后台 | P2 | 发送成功后按 Home 键，将企业微信切回后台。 |

## 4. 非功能需求

| 编号 | 需求 | 目标值 |
|------|------|--------|
| NF-01 | 消息采集延迟 | 后台 < 1 秒；前台（混合模式）< 5 秒；纯轮询 < 轮询间隔 + 3 秒。 |
| NF-02 | 消息去重准确率 | 重复消息误推率 < 0.1%。 |
| NF-03 | 自动回复成功率 | 正常网络与 UI 状态下 > 95%。 |
| NF-04 | 功耗（混合模式）| 空闲时 < 3mAh/小时；活跃时 < 8mAh/小时。 |
| NF-05 | 功耗（纯轮询模式）| 空闲时 < 6mAh/小时；活跃时 < 16mAh/小时。 |
| NF-06 | 最大监控群数 | 建议不超过 5 个，超过时 UI 提示风险。 |
| NF-07 | 本地消息队列容量 | 最多缓存 100 条待推送消息。 |
| NF-08 | 支持 Android 版本 | API 24（Android 7.0）及以上。 |
| NF-09 | 支持企业微信版本 | 适配主流版本，UI 结构变化时需更新节点 ID。 |

## 6. 状态机设计

`MessageCollector` 维护三种状态，状态切换由 `ForegroundDetector` 驱动：

| 状态 | 触发条件 | 采集行为 |
|------|---------|---------|
| `BACKGROUND` | 企业微信不在前台 | **混合模式**：仅 NotificationEventCollector 工作，UIPollingCollector 休眠。<br>**纯轮询模式**：UIPollingCollector 仍然工作（扫描列表页 → 发现新消息 → 启动企业微信 → 详情页读取）。 |
| `FOREGROUND` | 企业微信在前台 | UIPollingCollector 激活（按配置的轮询间隔扫描），NotificationEventCollector 保持监听作为辅助。 |
| `TRANSITION` | 前后台切换瞬间 | 持续 3 秒缓冲期，两种通道同时工作，去重器消峰。 |

**状态转换图：**

```
        企业微信切到前台                    企业微信切到后台
    ┌────────────────────┐            ┌────────────────────┐
    │                    ▼            │                    ▼
BACKGROUND ──────────────────→ TRANSITION ──────────────────→ FOREGROUND
    ▲                            (3秒)                            │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
                           企业微信切到后台
```

## 7. UI 轮询详细设计

### 7.1 企业微信消息列表页 UI 结构

基于 UI Dump 分析（2026-06-02）：

```
消息列表页 (package=com.tencent.wework)
└── RecyclerView (id=cxl, bounds=[0,264][1080,2205])  ← 消息列表容器
    ├── child0: LinearLayout  ← "全部/日程/会议" 标签栏
    ├── child1: RelativeLayout  ← 群聊项（可点击）
    │   ├── View (id=cxb)  ← 头像区域
    │   └── RelativeLayout (id=cx6)
    │       ├── TextView (id=hrm)  ← 群名，如 "智能客服测试2群"
    │       ├── TextView (id=g86)  ← 时间，如 "9:06"
    │       └── TextView (id=mar)  ← 消息摘要，如 "客服助理: [客服名片]..."
    ├── child2: RelativeLayout  ← 下一个群聊项
    └── ...
```

### 7.2 两阶段采集策略

由于消息列表页只能看到**最后一条消息的摘要**（`id=mar`），无法获取完整内容和发送者，因此采用两阶段策略：

**阶段一：列表页检测（快照比对）**

1. 获取消息列表 RecyclerView（`id=cxl`）。
2. 对每个配置的目标群：
   - 读取群名（`id=hrm`）、时间（`id=g86`）、摘要（`id=mar`）。
3. 与上一次轮询的快照对比，若 `mar` 或 `g86` 有变化 → 判定该群有新消息。

**阶段二：详情页读取（获取完整消息）**

对检测到有新消息的目标群：
1. 点击该群聊列表项（找 clickable 父节点 RelativeLayout）。
2. 等待进入聊天详情页（检测输入框出现 + 顶部标题匹配群名）。
3. 遍历聊天记录区域的 RecyclerView，提取所有**文本消息节点**。
4. 解析每条消息的**发送者昵称**和**消息内容**。
5. 过滤：跳过非文本类型、跳过自己发送的消息。
6. 按 Home 键返回消息列表页（或企业微信后台）。
7. 将完整消息提交到 `MessageDeduplicator`。

### 7.3 置顶群优化

用户将客服群**置顶**，这些群固定在 RecyclerView 的前几位：

- 轮询时**无需滚动列表**，直接扫描前 5 个可见项即可定位。
- 简化 `findGroupInCurrentScreen` 逻辑，提升定位速度。

### 7.4 聊天详情页消息解析

进入群聊详情页后，聊天记录通常也是一个 RecyclerView。消息气泡解析策略：
- 遍历聊天记录 RecyclerView 的可见子节点。
- 识别文本消息节点（排除图片、语音、表情等非文本）。
- 提取发送者昵称和消息内容。
- 由于 RecyclerView 只渲染可见区域，如需读取更早消息，需向上滑动加载。
- **默认只读取当前可见区域的未读消息**，不主动加载历史记录。

## 8. 监控模式

### 8.1 混合模式（HYBRID）— 默认

| 场景 | 采集方式 | 说明 |
|------|---------|------|
| 企业微信后台 | 通知监听 | 省电、实时，利用系统通知机制。 |
| 企业微信前台 | UI 轮询 | 填补通知盲区，主动扫描 UI 树提取完整消息。 |
| 切换瞬间 | 双通道并行（3秒缓冲）| 避免切换期间漏采，去重器消除重复。 |

**适用**：长期运行、追求省电、通知功能正常的手机。

### 8.2 纯轮询模式（POLLING_ONLY）

| 场景 | 采集方式 | 说明 |
|------|---------|------|
| 任何状态 | UI 轮询 | 不依赖通知权限和系统通知行为，全程无障碍扫描。 |
| 后台时 | 扫描列表页 → 发现新消息 → 启动企业微信 → 详情页读取 | 启动企业微信需要约 2-3 秒，增加延迟。 |
| 前台时 | 直接扫描 → 详情页读取 | 与混合模式前台行为一致。 |

**适用**：通知不稳定的环境（如部分 OPPO ColorOS 机型）、用户不愿依赖通知权限。

**代价**：耗电量比混合模式增加约 30-50%（后台状态也需要持续轮询）。

## 10. 后台接口契约

### 10.1 App → 后台（推送消息）

```http
POST {backendUrl}
Headers:
  X-API-Key: {apiKey}
  Content-Type: application/json

Body:
{
  "groupName": "智能客服测试2群",
  "sender": "张三",
  "content": "我想查一下我的卡号",
  "timestamp": 1717401600000,
  "deviceId": "abc123",
  "messageType": "text"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `groupName` | String | 消息来源群名称。 |
| `sender` | String | 发送者昵称。 |
| `content` | String | 消息文本内容。 |
| `timestamp` | Long | 消息时间戳（毫秒）。 |
| `deviceId` | String | 设备唯一标识（可选）。 |
| `messageType` | String | 固定为 `"text"`。 |

### 10.2 后台 → App（返回回复）

后台响应体支持以下格式：

**回复消息：**
```json
{
  "reply": "您好，请提供您的卡号后四位，我帮您查询。"
}
```

**不回复：**
```json
{
  "reply": null
}
```

**异步处理（后续再回复）：**
```json
{
  "reply": null,
  "async": true
}
```
App 收到 `async: true` 后，通过后续轮询或独立通道等待后台推送回复内容。

## 11. 自动回复编排

`AutoReplyOrchestrator` 负责串行调度回复任务：

```
后台返回回复 ──→ 消息队列 ──→ AutoReplyOrchestrator ──→ WeWorkUIAutomator
                                    │
                                    ├─ 检查企业微信是否在前台
                                    ├─ 在前台：直接执行 sendReply()
                                    ├─ 在后台：先启动企业微信 → 再执行 sendReply()
                                    └─ 执行完成后回调，处理队列中下一条
```

**串行保证：**
- 使用单线程 Handler 队列，确保同时只有一个回复任务在执行。
- 如果队列堆积超过 10 条，丢弃最早的任务并记录警告日志。

## 12. 错误处理与边界情况

| 场景 | 处理策略 |
|------|---------|
| 企业微信不在消息列表页 | UIPollingCollector 先按 Back 键回到列表页，再执行采集。 |
| 点击群聊后未进入详情页 | 超时 5 秒后放弃，记录日志，不影响下次轮询。 |
| 聊天详情页没有新消息（列表页误判） | 详情页读取时只提取**新于上次采集时间戳**的消息。 |
| 轮询期间用户手动操作手机 | 检测到窗口变化后，本轮轮询延迟到下次周期执行。 |
| 网络异常导致推送失败 | MessagePusher 本地队列缓存，最多保留 100 条，网络恢复后批量重试（指数退避）。 |
| 后台服务返回回复但 UI 自动化失败 | 记录失败日志，重试 2 次后放弃，不阻断后续消息处理。 |
| 企业微信被系统杀死 | 纯轮询模式下启动企业微信需要 2-3 秒，增加消息延迟，记录警告。 |
| 用户同时操作与自动化冲突 | 执行 UI 操作前检查当前窗口包名和 Activity，若发生变化则延迟执行。 |
| 目标群数量超过 5 个 | 配置页面提示"建议不超过 5 个群，否则可能导致消息延迟"。 |

## 13. 性能与耗电

### 13.1 轮询频率

| 场景 | 推荐间隔 | 说明 |
|------|---------|------|
| 默认 | 3000ms | 平衡实时性和功耗。 |
| 忙时（检测到新消息后）| 2000ms | 自适应频率，持续 3 轮后恢复默认。 |
| 闲时（连续 3 轮无新消息）| 5000ms | 自适应频率，降低功耗。 |
| 纯轮询模式 | 2000-3000ms | 建议比混合模式稍短，以弥补启动延迟。 |

### 13.2 耗电估算

以 **3 秒轮询间隔、3 个置顶群** 为例：

| 模式 | 场景 | 单次轮询 CPU 时间 | 每小时耗电 | 占 4500mAh 电池比例 |
|------|------|------------------|-----------|-------------------|
| 混合 | 空闲（无新消息）| 30ms | ~2mAh | 0.05% |
| 混合 | 活跃（每分钟 1 条）| 80ms | ~7mAh | 0.15% |
| 纯轮询 | 空闲 | 80ms | ~5mAh | 0.11% |
| 纯轮询 | 活跃 | 150ms | ~15mAh | 0.33% |

**对比参考：**
- 屏幕常亮：~300-500mAh/小时
- 微信正常使用：~100-200mAh/小时
- UI 轮询耗电约为微信正常使用的 **1/20**。

### 13.3 7×24 插电运行

- 现代手机充满后自动切换涓流/停充模式。
- UI 轮询几乎不发热（CPU 利用率 1-3%）。
- **长期插电 + 低负载轮询，对电池损耗可忽略不计。**

```xml
<service

    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"

```

### 15.2 无障碍服务配置

```xml
<!-- res/xml/accessibility_service_config.xml -->
<accessibility-service
    android:accessibilityEventTypes="typeNotificationStateChanged|typeWindowStateChanged|typeWindowContentChanged"
    android:accessibilityFeedbackType="feedbackGeneric"
```

## 16. 风险与限制

| 编号 | 风险 | 影响 | 缓解措施 |
|------|------|------|---------|
| R-01 | 企业微信 UI 升级，节点 ID 变化 | 高 | UI 轮询逻辑基于节点 ID（`cxl`, `hrm`, `mar` 等），企业微信版本升级可能导致 ID 变化，需及时更新适配。 |
| R-02 | 多群同时有新消息，串行处理延迟 | 中 | 限制目标群数量（建议 ≤5），批量读取详情页消息。 |
| R-03 | 用户手动操作与自动化冲突 | 中 | 执行 UI 操作前检查窗口状态，变化时延迟执行。 |
| R-04 | 部分系统限制后台启动 Activity | 中 | 先切回 App 自身前台，再启动企业微信（已有实现）。 |
| R-05 | 纯轮询模式下企业微信被系统杀死 | 中 | 每次轮询都需重新启动企业微信，增加 2-3 秒延迟。 |
| R-06 | 消息去重误判（不同消息内容相同）| 低 | 去重 Key 包含时间窗口（分钟级），降低误判概率。 |
