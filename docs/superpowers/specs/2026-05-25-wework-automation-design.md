# 企业微信外部群消息自动回复 - 设计方案

**日期**: 2026-05-25
**项目**: chaserpa (Android)
**技术栈**: Kotlin, Jetpack Compose, Android AccessibilityService, WebSocket, HTTP

---

## 1. 背景与目标

运营人员需要自动处理企业微信外部群消息，避免逐一人工回复。系统需实现：
1. 读取指定外部群的纯文本消息
2. 将消息推送到业务后台接口
3. 接收后台异步处理结果
4. 自动在对应群内回复

**使用者背景**: Java 后端开发，无 Android 开发经验。

---

## 2. 技术约束与方案选择

### 2.1 为什么只能走无障碍服务

| 方案 | 外部群消息 | 管理员权限 | 封号风险 | 可行性 |
|------|-----------|-----------|---------|--------|
| 企业微信官方 API | 不支持 | 需要 | 无 | 不可行 |
| 自建应用回调 | 不支持 | 需要 | 无 | 不可行 |
| Xposed/Frida Hook | 支持 | 不需要 | 极高 | 不可行 |
| 协议逆向 | 支持 | 不需要 | 极高 | 不可行 |
| **无障碍服务** | **支持** | **不需要** | **低** | **唯一可行** |

**结论**: 在不是企业管理员、不能承担封号风险的前提下，Android 无障碍服务是唯一现实路径。

### 2.2 后台推送方式选择

| 方案 | 实时性 | 复杂度 | Android 限制 | 推荐 |
|------|--------|--------|-------------|------|
| 轮询 (Polling) | 3-5秒延迟 | 低 | 无 | 备选 |
| **WebSocket** | **秒级** | **中** | **需处理断线** | **选定** |
| 长轮询 | 1-3秒 | 中 | 网络受限 | 不推荐 |

**选定 WebSocket**: 运营场景对延迟敏感，接受其实现复杂度。

## 3. 整体架构

```
┌─────────────────────────────────────────────────────┐
│              Android 前台服务 (chaserpa)              │
│                                                      │
│  ┌──────────────────────────────────────────────┐   │
│  │  企业微信 App                                 │   │
│  └──────────┬───────────────────────────────────┘   │
│             │ 无障碍事件                              │
│             ▼                                        │
│  ┌────────────────────┐    ┌────────────────────┐   │
│  │ MessageCollector   │    │    AutoReply       │   │
│  │   消息采集器        │    │    自动回复器       │   │
│  │  · 通知栏捕获      │    │  · 导航到目标群     │   │
│  │  · 节点遍历        │    │  · 填入文本         │   │
│  │  · 去重过滤        │    │  · 点击发送         │   │
│  └────────┬───────────┘    └────────▲───────────┘   │
│           │ HTTP POST JSON          │ WebSocket      │
│           ▼                         │ Push           │
│        业务后台 ←────────────────────┘                │
│           · 接收消息                                  │
│           · 业务处理                                  │
│           · WebSocket 推送回复                        │
└─────────────────────────────────────────────────────┘
```

### 3.1 数据流

1. 企业微信群有新消息 → 系统通知或界面内容变化触发无障碍事件
2. `MessageCollector` 解析出「群名 + 发送者昵称 + 消息文本」
3. 过滤：只处理白名单内的目标群；去重：同一内容 30 秒内不重复推送
4. `MessagePusher` 通过 HTTP POST 发送到后台（含 API Key）
5. 后台处理完后，通过 WebSocket 连接推送回复文本
6. `ReplyReceiver` 收到回复 → `AutoReply` 导航到对应群 → 填入文本 → 发送
7. 全程延迟：网络往返 + WebSocket 推送 + 无障碍模拟点击 ≈ 1-2 秒

## 4. 核心模块设计

### 4.1 无障碍服务注册 (WeWorkAccessibilityService)

继承 `AccessibilityService`，在 `AndroidManifest.xml` 中注册，监听以下事件：
- `TYPE_NOTIFICATION_STATE_CHANGED` — 通知栏消息（后台时）
- `TYPE_WINDOW_CONTENT_CHANGED` — 界面内容变化（前台群聊时）
- `TYPE_WINDOW_STATE_CHANGED` — 窗口切换（进入/离开群聊）

### 4.2 消息采集策略（双层捕获）

**第一层：通知栏捕获（企业微信在后台时）**
- 收到 `TYPE_NOTIFICATION_STATE_CHANGED` 事件
- 从 `Notification.extras` 直接读取：
  - `android.title` → 群名称
  - `android.text` → 消息内容
- 最可靠，无需解析 UI 节点

**第二层：界面节点遍历（企业微信在前台时）**
- 收到 `TYPE_WINDOW_CONTENT_CHANGED` 或当前在群聊窗口时
- 遍历 `AccessibilityNodeInfo` 树：
  - 查找群名节点（TextView）确认目标群
  - 查找消息列表容器（RecyclerView，resource-id 含 "list"）
  - 遍历消息气泡节点，提取发送者昵称和消息文本

**去重机制**
- 复合键：`群名 + 发送者昵称 + 消息内容 + 时间窗口（30秒内）`
- 使用内存 `LruCache` 存储最近 100 条消息的 hash

**目标群过滤**
- 配置白名单 `Set<String>`，只处理白名单内的群

### 4.3 后台通信

**HTTP 推送（手机 → 后台）**
```
POST {backend_url}/api/message
Headers: X-API-Key: {api_key}
Content-Type: application/json

Body:
{
  "groupName": "某某客户群",
  "sender": "客户昵称",
  "content": "消息文本",
  "timestamp": 1716624000000
}
```

**WebSocket 接收（后台 → 手机）**
```json
{
  "type": "reply",
  "targetGroup": "某某客户群",
  "content": "回复内容",
  "messageId": "uuid-from-backend",
  "timestamp": 1716624000000
}
```

**WebSocket 客户端要求**
- 连接地址从配置读取
- 断线重连：指数退避策略（1s → 2s → 4s → 8s，最大 60s）
- 心跳：每 30 秒发送 `{"type":"ping"}`
- 连接状态上报：连接成功/断开时通过 HTTP 或日志通知

### 4.4 自动回复 (AutoReply)

**执行流程**
1. 收到 WebSocket `reply` 消息
2. 调用 `AutoReply.sendReply(targetGroup, content)`
3. **Step 1 - 定位目标群**
   - 当前已在该群界面？→ 直接进入 Step 2
   - 不在？→ 通过搜索导航（见下方策略）
4. **Step 2 - 填入文本**
   - 查找输入框节点（EditText，resource-id 含 "input"）
   - `performAction(ACTION_SET_TEXT, content)`
5. **Step 3 - 点击发送**
   - 查找发送按钮（text="发送" 或 content-desc="发送"）
   - `performAction(ACTION_CLICK)`
6. **Step 4 - 发送回执**
   - 通过 WebSocket 或 HTTP 上报：`messageId` 已发送成功

**导航到目标群的策略**
1. **搜索导航（推荐）**：点击搜索框 → 填入群名 → 点击搜索结果 → 进入群聊
2. **通知栏直达**：如有该群通知，点击通知进入（不可控，仅作优化）
3. **缓存兜底**：导航失败时缓存回复内容，下次进入该群时自动检测并发送

**串行队列**
- 连续多条回复维护一个队列，串行执行，避免并发导致 UI 混乱

## 5. 分阶段实现策略

### 阶段一：消息采集 + HTTP 推送（MVP）

**目标**: 验证"能读到消息并推给后台"。

**功能范围**:
- 无障碍服务基础框架注册和启动
- 双层消息采集：通知栏抓取 + 界面节点遍历
- 消息去重与目标群过滤
- HTTP POST 推送消息到后台（含 API Key）
- 极简配置界面：输入后台地址、API Key、目标群白名单

**验收标准**: 在群里发消息 → 后台成功收到 JSON 推送。

### 阶段二：WebSocket + 自动回复闭环

**目标**: 实现完整的"消息 → 后台 → 回复"自动化闭环。

**功能范围**:
- WebSocket 客户端：连接后台、断线重连、心跳保活
- 接收后台的 `reply` 指令并解析
- `AutoReply` 模块：导航到目标群、填入文本、点击发送
- 发送回执：回复成功后通知后台

**验收标准**: 群里发消息 → 后台处理 → 群里自动收到回复。

### 阶段三：稳定性与工程化

**目标**: 让系统能在真实运营环境中 7x24 稳定运行。

**功能范围**:
- 前台服务 + 常驻通知栏（防止系统杀进程）
- 手机保活引导：忽略电池优化、自启动权限
- 日志系统：关键节点打日志，便于排查问题
- 配置持久化（DataStore）：配置不随 App 重启丢失
- 错误处理与降级：接口超时、WebSocket 断线、节点查找失败的兜底策略

**验收标准**: 手机锁屏静置 1 小时后，仍然能正常收发消息。

## 6. 边界情况处理

| 情况 | 处理策略 |
|------|---------|
| 企业微信不在前台 | 先通过 Intent 拉起企业微信，再执行导航 |
| 输入框被键盘遮挡 | 点击输入框触发聚焦，系统自动弹出键盘 |
| 发送按钮不可点击 | 重试填入文本，或上报发送失败 |
| 连续多条回复 | 维护队列，串行执行 |
| 导航超时（5秒） | 放弃本次回复，上报"发送失败"，后台决定重试 |
| WebSocket 断线 | 指数退避重连，期间消息仍通过 HTTP 推送，回复暂存 |
| 无障碍服务被系统关闭 | 引导用户重新开启，前台服务发送告警通知 |

## 7. 风险与降级策略

| 风险 | 影响 | 降级策略 |
|------|------|---------|
| 企业微信升级导致 UI 结构变化 | 消息采集/回复失效 | 增加日志告警，快速定位变化的节点特征；必要时降级为仅通知栏捕获 |
| 无障碍服务被手机厂商杀后台 | 整个系统失效 | 前台服务 + 保活引导；提供手动重开入口 |
| WebSocket 长期无法连接 | 只能发消息不能收回复 | HTTP 推送不受影响，回复功能降级为"后台处理，人工查看后再手动发" |
| 节点查找频繁失败 | 自动回复成功率低 | 增加缓存兜底 + 搜索导航重试机制 |
